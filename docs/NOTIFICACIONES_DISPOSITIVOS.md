# Notificaciones: identidad de destinatarios

El Centro de notificaciones lista y cuenta destinos únicos con token habilitado. `notification_devices.js` agrupa por igualdad exacta de `installId`, `pushToken`, `deviceKey` o `notificationGroupId`, siempre dentro del mismo dominio. Las relaciones son transitivas para contemplar cambios de token e instalación. `notificationGroupId` se asigna sólo tras confirmación del operador; nunca se deduce por modelo. El registro más reciente con token vigente determina el destinatario y se conserva el alias disponible.

El GET del panel y el POST de envío usan la misma agrupación. Una selección antigua se resuelve contra todos los registros habilitados del dominio: seleccionar dos identificadores vinculados envía una sola notificación. La respuesta pública no expone tokens Firebase, agentes de usuario ni listas internas de identificadores. El panel indica cuántos registros están vinculados y cuenta destinos únicos.

No se borran ni fusionan documentos Mongo, preferencias, autenticaciones ni turnos. No se identifica un teléfono por modelo, IP o user agent: diferentes celulares pueden compartirlos. Registros sin relación verificable se conservan separados. Mecan 1.0.6 envía `deviceKey`, SHA-256 de un namespace, paquete y ANDROID_ID; nunca el identificador Android en claro. Está limitado a la combinación de app/firma, usuario Android y equipo; puede cambiar por restauración de fábrica o cambio de firma. No se usa para autenticación ni para recuperar propiedad de turnos. Conserva installId y datos existentes. IDs ausentes o conocidos como no únicos no generan deviceKey. El backend sólo almacena deviceKey si son 64 caracteres hexadecimales; una llamada web sin ese campo no borra el valor existente.

Sólo un error estructurado Firebase `UNREGISTERED` retira un token del listado de destinos, conservando el documento. La marca contiene su hash en `notificationInvalidTokenHash`: un token nuevo vuelve a habilitar el registro sin cambiar permisos de cola. No marcar como inválidos errores de red, cuota, permisos o credenciales. La herramienta `deploy/validate-notification-tokens.cjs` usa exclusivamente `validate_only:true`, no entrega mensajes, y registra el resultado en el servidor. Un resultado válido no demuestra que la app siga instalada ni que vaya a recibir un envío.

Verificación: `node --test tests/notification_devices*.test.js` cubre agrupación transitiva, aislamiento de dominios, modelos iguales con identidades diferentes, selección de alias anteriores, envío único y ausencia de tokens en la respuesta pública. Los envíos de las pruebas usan Firebase simulado, nunca clientes reales.

## Operación confirmada el 1/11/2026

Auditado AWS `ip-172-26-0-152`, Mongo `Cluster0` en `127.0.0.1`. MCN tenía 67 registros y 22 OnePlus con identificadores y tokens distintos; el usuario confirmó expresamente que los 22 eran un mismo teléfono de prueba. Se vincularon mediante `notificationGroupId=verified-mcn-oneplus-20261101`. La validación Firebase revisó 31 tokens: 27 aceptados y cuatro UNREGISTERED. Se marcaron sólo esos cuatro tras volver a comparar el hash actual; no se enviaron notificaciones reales.

Respaldo de los campos modificados antes de la vinculación: `/var/backups/asisto/notification-devices-before-link-20261101.json`, protegido en AWS; auditoría en `notification-token-validation-20261101.json` del mismo directorio. No contienen claves Firebase ni tokens en claro. Conservar ambos para trazabilidad y reversión.

Publicación acotada 5.00.326: AWS principal `v5.00.326-notification-devices-20261101-2`; turnero AWS y Mecan local `v5.00.326-notification-devices-20261101-3`. Los tres servicios activos y healthz correctos. Preserva variantes de runtime, historial y módulos de cola. Se actualizó también la agrupación del centro de aplicaciones donde estaba presente. Dos intentos preparatorios fallaron antes de cambiar current; no se activaron esas copias.

Verificación del GET real con la base productiva: MCN devuelve cinco destinos habilitados (cuatro activos a 30 días), OnePlus una sola fila con 22 registros; historial conserva 15 envíos correctos.
